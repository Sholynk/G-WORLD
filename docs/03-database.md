# G WORLD — Database Design (Cloudflare D1 / SQLite)

The logical database name is **`g_world`**. The physical `database_id` is issued by Cloudflare
(`wrangler d1 create g_world`) and configured in `apps/api/wrangler.jsonc`; IDs never live in code.

> **D1 is SQLite, not MySQL.** No `AUTO_INCREMENT`, no `ENGINE=InnoDB`, no `UNSIGNED`, no `ENUM`,
> no `NOW()`. Conventions used here: `TEXT` primary keys (prefixed ids), `TEXT` ISO-8601 UTC
> timestamps (`2026-10-16T09:31:07.412Z`), `INTEGER` 0/1 booleans with `CHECK` constraints, and
> `CHECK (col IN (...))` instead of enum types.

## 1. Conventions

| Concern | Rule |
| --- | --- |
| Primary keys | `TEXT` ids like `usr_01J9…` generated by `lib/ids.ts` (sortable, non-guessable enough for internal use; public codes are separate) |
| Timestamps | `created_at`/`updated_at` `TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))`, kept fresh by triggers |
| Booleans | `INTEGER NOT NULL DEFAULT 0 CHECK (col IN (0,1))` |
| Money/PII | none collected by default; only what the learning experience needs |
| Deletes | Academic hierarchy uses `ON DELETE RESTRICT`/`CASCADE` deliberately; content is **archived**, not deleted, so progress records never dangle |
| Enums | `CHECK (status IN ('draft','published','archived'))` |
| Indexes | Every foreign key and every column used in a `WHERE`/`ORDER BY` hot path is indexed (migration `0005`) |
| Migrations | Additive and forward-only; never edited after being applied to any environment |

Foreign keys are enforced by SQLite only when `PRAGMA foreign_keys = ON`. D1 enables this per
connection by default, and every migration sets `PRAGMA foreign_keys=ON;` explicitly at the top.

## 2. Domain A — Users and access (`0001_users_and_access.sql`)

| Table | Purpose | Key columns |
| --- | --- | --- |
| `roles` | Role catalogue | `key` UNIQUE (`public`,`student`,`admin`,`super_admin`), `rank`, `is_system` |
| `permissions` | Atomic capability catalogue | `key` UNIQUE (`course.write`, `user.read.any`, `audit.read`, …) |
| `role_permissions` | Role → permission grants (many-to-many) | PK `(role_id, permission_id)` |
| `users` | Every account, including admins | `email` UNIQUE NOCASE, `password_hash`, `password_algo`, `role_id` FK, `status`, `email_verified_at`, `failed_login_attempts`, `locked_until` |
| `student_profiles` | Optional student details, 1:1 with users | `user_id` PK FK, `student_number` UNIQUE, `display_name`, `education_level`, `country`, `interests_json` |

Notes
- Passwords are **never** stored in plaintext: `password_hash` holds `pbkdf2$sha256$<iterations>$<salt>$<hash>`
  (see ADR-0004) and `password_algo` allows future algorithm migration.
- `users.status ∈ {pending_verification, active, suspended, deactivated}`.
- A user has exactly one role (`role_id`); the role↔permission mapping makes future multi-role
  support additive rather than a breaking change.
- `last_login_at`, `failed_login_attempts`, `locked_until` support brute-force defence.

## 3. Domain B — Platform and security data (`0002_platform_and_security.sql`)

| Table | Purpose |
| --- | --- |
| `user_sessions` | Database-backed sessions: `token_hash` UNIQUE (SHA-256 of the cookie value), `expires_at`, `revoked_at`, `last_seen_at`, `ip_hash`, `user_agent` |
| `qr_codes` | Student identity + certificate verification codes: `code` UNIQUE, `user_id` FK, `kind ∈ {student_id, certificate}`, `scan_count`, `revoked_at` |
| `notifications` | In-app notices: `user_id` (NULL = broadcast), `type`, `title`, `body`, `link_url`, `read_at` |
| `email_messages` | Outbox/audit of every outbound email: `to_email`, `subject`, `body_text`, `provider`, `status ∈ {queued,sent,failed}`, `error`, `sent_at`. Powers `EMAIL_PROVIDER=console` in dev and delivery debugging in prod |
| `email_verification_tokens` | Single-use `token_hash` UNIQUE, `expires_at`, `consumed_at` |
| `password_reset_tokens` | Single-use `token_hash` UNIQUE, `expires_at`, `consumed_at`, `requested_ip_hash` |
| `audit_logs` | Append-only trail: `actor_user_id`, `actor_role`, `action`, `entity_type`, `entity_id`, `metadata_json`, `ip_hash`, `user_agent`, `created_at` |
| `rate_limits` | Fixed-window counters: PK `key` (`login:ip:<hash>`, `register:ip:<hash>`, …), `window_start`, `count`, `blocked_until` |

Sessions are **not** JWTs — see ADR-0003. Raw session tokens exist only in the user's httpOnly
cookie; the database stores their SHA-256 hash, so a database leak does not permit session hijacking.

## 4. Domain C — Academic content (`0003_academic_content.sql`)

```
departments ──1:N──► subjects ──1:N──► courses ──1:N──► modules ──1:N──► lessons
                                          │                                  ├──1:N──► videos
                                          ├──N:M──► skills (course_skills)   └──1:N──► resources
                                          └──1:N──► resources (course-level)
```

| Table | Notable columns |
| --- | --- |
| `departments` | `name` UNIQUE, `slug` UNIQUE, `icon`, `image_url`, `display_order`, `status` |
| `subjects` | `department_id` FK RESTRICT, UNIQUE `(department_id, name)`, `slug` UNIQUE, `status` |
| `courses` | `subject_id` FK RESTRICT, `slug` UNIQUE, `summary`, `description`, `learning_outcomes_json`, `prerequisites_json`, `difficulty ∈ {beginner,intermediate,advanced}`, `estimated_minutes`, `thumbnail_url`, `instructor_name`, `status`, `is_featured`, `published_at`, `created_by` |
| `skills` | `slug` UNIQUE, `category` |
| `course_skills` | `kind ∈ {required, acquired}`, `weight`, PK `(course_id, skill_id, kind)` |
| `modules` | `course_id` FK CASCADE, `position`, `status`, UNIQUE `(course_id, position)` |
| `lessons` | `module_id` FK CASCADE, `slug`, `content_md`, `position`, `estimated_minutes`, `is_preview`, `completion_rule ∈ {view,mark_complete,quiz_pass}`, `status` |
| `videos` | `lesson_id` FK CASCADE, `provider='youtube'`, `provider_video_id`, `position`, `duration_seconds`, `is_primary` |
| `resources` | `lesson_id` NULL-able FK CASCADE **or** `course_id` NULL-able FK CASCADE (exactly one set), `kind ∈ {pdf,link,article,download}`, `url`, `r2_key`, `size_bytes` |

`is_preview` on lessons is what lets the public catalog show a genuine lesson preview to visitors
without exposing enrolled-course content.

## 5. Domain D — Learning and assessment (`0004_learning_and_assessment.sql`)

| Table | Notable columns / constraints |
| --- | --- |
| `enrollments` | UNIQUE `(user_id, course_id)`, `status ∈ {active,completed,cancelled,expired}`, `progress_percent` (0–100 CHECK), `last_lesson_id`, `completed_at` |
| `lesson_progress` | UNIQUE `(enrollment_id, lesson_id)`, `status ∈ {not_started,in_progress,completed}`, `seconds_spent`, `completed_at` |
| `quizzes` | course/module/lesson scoped, `pass_mark_percent`, `max_attempts`, `time_limit_minutes`, `shuffle_questions`, `status` |
| `quiz_questions` | `question_type ∈ {single_choice,multiple_choice,true_false,short_answer}`, `points`, `explanation`, `position` |
| `quiz_options` | `question_id` FK CASCADE, `label`, `is_correct`, `position` — correct flags are **never** sent to students before submission |
| `quiz_attempts` | UNIQUE `(quiz_id, user_id, attempt_number)`, `score_points`, `max_points`, `score_percent`, `passed`, `status ∈ {in_progress,submitted,graded,abandoned}` |
| `quiz_answers` | `attempt_id` FK CASCADE, `selected_option_ids_json`, `answer_text`, `is_correct`, `points_awarded` |
| `assignments` | scoped like quizzes, `max_points`, `due_at`, `allow_late` |
| `assignment_submissions` | UNIQUE `(assignment_id, user_id, attempt_number)`, `submission_text`, `r2_key`, `link_url`, `status ∈ {submitted,graded,returned,resubmit_requested}`, `graded_by` |
| `certificates` | UNIQUE `(user_id, course_id)`, `enrollment_id` UNIQUE, `certificate_number` UNIQUE, `verification_code` UNIQUE, `issued_at`, `revoked_at` |
| `course_reviews` | UNIQUE `(course_id, user_id)`, `rating` CHECK 1–5, `status` — scaffolded for the post-MVP review feature |

Derived rules implemented in `lib/progress.ts` and `lib/certificates.ts` (unit-tested):

```
progress_percent = completed_lessons / publishable_lessons * 100   (integer, floor)
enrollment.status = 'completed'  when progress_percent == 100 and publishable_lessons > 0
certificate issued once per (user, course) when the enrollment completes
quiz passed      = score_percent >= quiz.pass_mark_percent
```

## 6. Read models — views (`0006_analytics_views.sql`)

| View | Consumers |
| --- | --- |
| `v_published_courses` | Public catalog + search (joins department + subject, counts modules/lessons/enrollments) |
| `v_course_curriculum` | Course detail page (modules → lessons ordered) |
| `v_enrollment_progress` | Student dashboard + admin enrollment table |
| `v_quiz_attempt_summary` | Student quiz history and pass rates |
| `v_department_stats` | Home page and admin KPI cards |
| `v_admin_activity` | Audit log screen (joined with actor email/role) |

Views keep the most-frequently-joined shapes in one place, so a route handler stays a one-liner
and the SQL stays reviewable.

## 7. Reference data (`0007_reference_data.sql`)

Idempotent (`INSERT OR IGNORE`) seeding of roles, the permission catalogue and the role→permission
map:

| Role | Rank | Granted permissions (summary) |
| --- | --- | --- |
| `public` | 0 | none (unauthenticated baseline) |
| `student` | 10 | `course.read`, `enrollment.own.*`, `progress.own.*`, `certificate.own.read`, `qr.own.read` |
| `admin` | 50 | student/role-safe reads, all content write, assessments, certificates, analytics, `audit.read`, `qr.scan` |
| `super_admin` | 90 | everything `admin` has + `user.role.write`, `admin.manage`, `settings.write` |

## 8. Migration workflow

```bash
# create the database once (developer machine, authenticated wrangler)
wrangler d1 create g_world            # copy the database_id into apps/api/wrangler.jsonc

# local development
npm run db:migrate:local              # applies database/migrations/*.sql in order
npm run db:seed:local                 # demo catalog + dev accounts (never for production)
npm run db:reset:local                # wipe + re-migrate + re-seed

# production (CI or manual, deliberate)
npm run db:migrate:remote             # wrangler d1 migrations apply g_world --remote

wrangler d1 migrations list g_world --local --config apps/api/wrangler.jsonc
```

Rules
1. Migrations are numbered, forward-only and reviewed like code; a merged migration is immutable.
2. Additive first: add nullable column → backfill → add constraint in a later migration.
3. Destructive changes ship as *expand → migrate → contract* across at least two releases.
4. Every migration must apply cleanly to an empty local database **and** to a database that already
   has the previous migrations applied — CI runs both paths (`tests/integration` + `db:reset:local`).
5. Seeds are separate from migrations so that production never receives demo data.
6. Because D1 is SQLite, `ALTER TABLE` support is limited: table rewrites are done explicitly
   (create new → copy → drop → rename) inside a transaction.
